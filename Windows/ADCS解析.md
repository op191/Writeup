这五个概念基本构成了理解 AD CS 和 ESC 攻击的核心。它们分别回答五个不同的问题：

- ACL：谁有权操作证书模板？

- EKU：这张证书允许用于什么用途？

- SAN：证书里声明了哪些身份信息？

- CA 签发策略：CA 在什么条件下愿意签发证书？

- 证书映射机制：认证系统如何确定这张证书属于哪个账户？

先理解正常设计，再看这些机制如何组合出攻击面。

## 一、先看完整的证书认证过程

① ACL：申请者有资格吗？

检查用户对模板、CA 等对象的访问权限

② CA 签发策略：申请能通过吗？

检查模板配置、审批、授权及其他签发条件

③ EKU + SAN：证书包含什么？

EKU 描述用途；SAN 可包含用户或计算机身份信息

④ 证书映射：证书对应谁？

认证系统根据证书信息、映射规则和账户信息确定身份

⑤ 身份认证与授权

验证通过后，账户仍然只能执行其被授权的操作

这是概念上的简化流程。实际中，部分检查会发生在不同组件上，顺序也不完全固定。

## 二、ACL：谁能操作模板？

ACL 是 Access Control List，即访问控制列表。

在 AD CS 中，证书模板是 Active Directory 中的对象。模板 ACL 决定不同主体对该对象可以执行哪些操作。

常见权限包括：

| 权限         | 含义                  |
| ---------- | ------------------- |
| Read       | 读取模板属性              |
| Enroll     | 申请该模板的证书            |
| Autoenroll | 符合条件时自动注册证书         |
| Write      | 修改对象的部分属性，具体取决于 ACE |
| WriteDacl  | 修改对象的访问控制列表         |
| WriteOwner | 修改对象所有者，具体后果取决于后续权限 |

例如，某个模板允许 `Domain Users` 申请证书，这只说明该组具备申请权限，并不意味着每个域用户都能冒充管理员。

真正需要关注的是：申请者能否控制关键模板属性、是否可以指定身份，以及该模板能签发什么用途的证书。

与 ESC 的关系： ESC1 主要涉及危险的模板配置；ESC4 则涉及对模板具有不当修改权限的情形。

## 三、EKU：证书能用于什么？

EKU 是 Extended Key Usage，即增强型密钥用法。

它是证书中的扩展字段，用于表达证书预期的用途。

常见 EKU：

| 用途                    | OID                      |
| --------------------- | ------------------------ |
| Client Authentication | `1.3.6.1.5.5.7.3.2`      |
| Server Authentication | `1.3.6.1.5.5.7.3.1`      |
| Smart Card Logon      | `1.3.6.1.4.1.311.20.2.2` |
| Code Signing          | `1.3.6.1.5.5.7.3.3`      |

举例来说：

- Server Authentication 通常用于证明服务器身份。

- Client Authentication 可用于支持客户端证书认证的服务。

- Code Signing 用于代码签名场景。

为什么这与 AD CS 攻击有关？

因为即使攻击者取得了一张有效证书，如果该证书不适用于目标认证场景，也不一定能用它完成身份认证。

不过，EKU 并不是简单的万能开关。实际结果还取决于证书策略、应用程序、KDC 和系统版本等条件；缺少 EKU 也不必然意味着证书不能用于认证。

## 四、SAN：证书声明了哪些身份？

SAN 是 Subject Alternative Name，即主题备用名称。

它是证书中的身份信息扩展，可以包含：

- DNS 名称

- RFC822 邮箱地址

- IP 地址

- UPN（User Principal Name）等其他名称形式

在 AD 环境中，UPN 相关信息尤其值得关注，因为它可能参与将证书关联到用户账户的过程。

例如，一张证书可能包含：

```
Subject:
    CN=some-user

Subject Alternative Name:
    UPN=some-user@domain.local
    DNS=host.domain.local
```

这里需要区分两个问题：

1. 证书写了什么身份信息？ 这是 SAN 解决的问题之一。

2. 系统是否信任这些信息，并据此把证书映射到某个账户？ 这是证书映射机制的问题。

证书里出现某个用户的 UPN，不代表认证系统就必然接受它作为该用户的身份凭据。

与 ESC 的关系： 在 ESC1 这类情形中，申请者能够影响证书中的主体身份信息，是重要的风险条件之一。但还需要结合 EKU、模板配置、签发权限及映射规则判断。

## 五、CA 签发策略：谁能让 CA 签出证书？

CA 是 Certificate Authority，即证书颁发机构。

CA 使用自己的私钥对证书签名，使信任该 CA 的系统能够验证证书的签发来源和完整性。

这里要区分三个层次：

- 模板权限：谁能申请某个模板？

- 模板配置：证书包含哪些属性、用途和身份信息？

- CA 策略与配置：申请需要满足什么条件，是否需要审批，CA 是否发布该模板等？

例如，模板即使允许用户自行提供某些身份字段，如果 CA 还要求严格审批，或者模板没有发布，申请者也未必能获得证书。

反过来，如果多个限制同时配置不当，CA 就可能签发一张由低权限用户申请、却能被用于高权限身份认证的证书。

CA 的签名只证明证书由该 CA 签发且签名有效，不等于证书所声明的身份一定合理，更不等于申请者本来就有权使用该身份。

## 六、证书映射机制：证书最终代表谁？

这是理解 AD CS 身份冒充问题时非常关键的一层。

证书映射机制负责将证书关联到 Active Directory 中的账户。具体依据可能包括：

- 证书中的 UPN 等身份信息

- 账户中的相关属性

- 证书与账户之间的显式映射关系

- 强证书映射所使用的标识信息

- Windows 版本、更新状态和域控制器的映射策略

例如，用户提交一张证书进行 Kerberos PKINIT 认证时，KDC 不只是检查“这张证书有没有 CA 签名”，还需要确定证书对应哪个账户。

可以把它抽象为：

```
证书
  │
  ├── 签名与信任链是否有效？
  ├── 是否满足证书用途要求？
  ├── 身份信息是否符合映射规则？
  │
  ▼
映射到 AD 账户
  │
  ▼
验证通过后，才可能获得该账户对应的 Kerberos 身份
```

如果映射策略存在问题，或者证书的身份信息与映射规则组合产生了不安全的结果，就可能出现证书被用于冒充其他账户的情况。

需要注意，Windows 已经引入并持续强化证书到账户的强映射要求，因此旧教程中的部分证书冒充方式，在更新后的环境中可能不再有效。

## 七、把五个概念联系到 ESC

| 概念      | 核心检查问题     | 典型风险                 |
| ------- | ---------- | -------------------- |
| ACL     | 谁能申请、修改模板？ | 低权限主体获得过大的申请或修改权限    |
| EKU     | 证书可用于什么？   | 证书用途与认证场景相匹配，且其他条件允许 |
| SAN     | 证书声明谁的身份？  | 申请者能控制本不应由其控制的身份字段   |
| CA 签发策略 | CA 为什么会签发？ | 审批、模板发布或其他限制配置不当     |
| 证书映射    | 系统把证书认作谁？  | 证书身份被不当映射到目标账户       |

它们不是五个互相独立的漏洞，而是证书签发与认证体系中相互关联的安全控制。

例如，ESC1 的判断不能简化为“模板允许域用户申请”。需要检查申请权限、客户端认证用途、申请者能否指定主体信息、审批要求以及目标环境的证书映射策略等条件。

## 八、建议你按这个顺序学习

你目前正在用 Certipy 研究 AD CS，可以按以下顺序推进：

1. ACL：理解模板的 `Enrollment Rights`、`WriteDacl` 和 `WriteOwner`。

2. EKU：弄懂为什么一张证书的用途会影响认证结果。

3. SAN 与 Subject：理解 UPN、DNS 名称和证书主体之间的区别。

4. CA 策略：理解模板发布、审批和签发权限。

5. 证书映射：研究证书如何用于 Kerberos PKINIT，以及强映射策略如何影响认证。

学完后，再把 ESC1、ESC4、ESC8 和 ESC9/ESC10 逐一映射到这些机制上，就不必靠死记编号来判断风险了。

下一步最值得深入的是证书映射机制：它能解释为什么一张签名完全有效的证书，仍然可能导致身份冒充，也能解释为什么某些旧版 AD CS 攻击教程在新系统上失效。
