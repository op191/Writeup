wmiexec.py 之所以更"安静"，核心在于它走的不是"建服务"这条路，而是利用WMI（Windows Management Instrumentation，Windows自带的系统管理接口）来执行命令。同样按步骤拆开讲：

**wmiexec的整个流程**

1. **同样先通过SMB（445端口）做身份验证**，这一步跟psexec一样，没法避免——毕竟都得先证明自己有权限。

2. **不上传任何exe文件，也不创建服务**。而是直接通过 **DCOM/WMI接口**（走135端口 + 一个动态分配的高位端口，这个通道叫做 `RPC`），调用WMI里一个叫 `Win32_Process` 的类，执行它的 `Create` 方法——这个方法的作用就是"在目标机器上启动一个新进程"，本质上跟你在目标机器上手动打开任务管理器新建一个进程是同一个系统功能，只是通过远程调用触发的。

3. **命令的输出怎么拿回来**：因为WMI本身不像PsExec那样能直接建立一个交互式的双向管道，wmiexec用了个取巧的办法——**把命令执行结果重定向输出到目标机器 `ADMIN$` 共享下的一个临时文件里，然后再通过SMB把这个文件读回来显示给你，读完再删掉**。所以你看到的"交互式shell"效果，其实是每敲一条命令，wmiexec在后台悄悄"执行→写临时文件→读取→删除"这一套动作，伪装成实时交互的样子。

**为什么这样更隐蔽**

对比psexec的几个"吵"的动作，wmiexec对应地规避了：

| PsExec的动作 | 对应风险 | WMIexec怎么规避 |
|---|---|---|
| 上传随机命名的exe到磁盘 | 容易被文件监控/杀软扫到 | 不落地任何exe文件 |
| 调用CreateServiceW建服务 | 触发Event ID 7045这种高危日志 | 完全不碰服务控制管理器(SCM)，不产生这类日志 |
| 服务以SYSTEM权限跑 | 权限一目了然、行为模式固定 | 进程是以你认证的那个用户权限跑的（不是SYSTEM），行为更贴近正常管理操作 |

**代价（trade-off）**

- **权限没有psexec高**：因为不走"服务=SYSTEM"这条路，wmiexec给你的是**你验证身份时用的那个账户的权限**，不是自动变成SYSTEM。如果你认证用的账户本身不是管理员/SYSTEM级别，拿到的shell权限就相应受限。
- **仍然不是完全没痕迹**：WMI调用本身也会在日志里留下记录（比如Sysmon如果配置了监控WMI活动的规则，或者目标开了WMI相关的审计日志），只是比PsExec那种"建服务+写日志"的组合特征弱得多、更容易和正常的系统管理行为混在一起，属于"相对安静"而不是"完全无痕"。

一句话对比记忆：**PsExec = 建一个临时服务来跑代码（吵、但给SYSTEM权限）；WMIexec = 借用WMI的远程进程创建能力跑代码（安静、但权限跟你认证账户一致）**。

实战里选哪个，通常看你的目标：需要SYSTEM权限做进一步提权/dump凭据，就用psexec或者smbexec；只是想低调地执行个命令看看权限/信息，wmiexec更合适。
